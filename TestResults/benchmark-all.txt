=== Primitive BLAS kernels (Level-1 & Level-2) ===
Isolates the kernels every solver bottoms out on. The signal is the float-vs-double
GFLOP/s ratio at large N: ~2x => the inner loop vectorises, ~1x => it runs serial
(headroom for the multi-accumulator rework). Reductions (vecDot/L1/L2/LInf/sum) are
serial acc-chains; GEMV is a per-row reduction; vecMat (Aᵀx) and axpy are the
already-vectorising baselines.
Level-1 REPS=512, Level-2 REPS=64 back-to-back calls per timed sample.

=== Dense vs Sparse (BSR) iterative solvers: timing + numerical cross-check ===
Same matrix, two storage forms: a dense NxN floatMxN/doubleMxN with zeros in the
absent blocks, and a floatBSR/doubleBSR (block-CSR) holding exactly the nonzero
b=3 blocks. Because both encode the IDENTICAL matrix, (a) dense-vs-sparse time is
directly comparable (same math, only storage/traversal differs), and (b) dense-vs-
sparse SOLUTIONS must agree numerically -- the residual column is that cross-check,
always computed from the DENSE reference matrix. maxIter is FIXED with
tol=0, so every sample runs exactly K iterations (deterministic timing,
mirroring IterativeBenchmark.cs); residual after K iterations shows how converged
(not just how fast) each path is. Block density is at the BLOCK level (nb x nb
block grid): ~7% / ~33% of blocks nonzero, always including every diagonal block.
Section 0 first isolates the pure per-iteration operator cost (dense GEMV vs sparse
spMV) that dominates every solver -- the cleanest dense-vs-sparse signal. Section 0b
goes one level deeper: symmetric lower-block storage (Symmetric=true, ToBSRSymmetric)
vs full block-CSR storage on the IDENTICAL SPD matrix -- bsrMatVecSym touches half as
many stored blocks as the full traversal, so this isolates that ~2x memory/FLOP win.
Section 1x is a dedicated N=1024 CG-only case at b=4 (256 blocks of 4x4, an unrolled
kernel size) -- 1024 isn't divisible by the b=3 workhorse size Section 1 sweeps.
